# @astronomic/ui

Restylable Astro components driven by semantic `--ui-*` tokens. Use only token-based classes, and never the `dark:` variant: dark mode swaps the token values.

Works in any plain Astro site. EmDash is supported but never required: nothing here imports `emdash`, and components take plain props (strings, arrays of plain objects, slots), never CMS objects.

## Setup in a site

Needs Astro 7 and Tailwind v4 (`@tailwindcss/vite`). No React: the interactive parts (the menu, the mode switch, the forms) are native HTML with small scripts. (Pro's `Tabs` is a React island and needs `@astrojs/react` with `react`, `react-dom` and `@base-ui/react`.)

In the site's main CSS file:

```css
@import "tailwindcss";
@import "@astronomic/ui/tokens.css";
@import "@astronomic/ui/theme.css";
@import "@astronomic/ui/presets/soft.css"; /* optional: a preset, after tokens.css */

/* Tailwind skips node_modules, so point it at the component source.
   The path is relative to this CSS file (here: src/styles/global.css). */
@source "../../node_modules/@astronomic/ui/src";
```

Without the `@source` line the components render unstyled.

Without a preset you get the default look, Minimal. The presets in `@astronomic/ui/presets/`:

| Preset | File | Fonts | Fontsource packages |
| --- | --- | --- | --- |
| Minimal (default) | none, `tokens.css` alone | Geist | `@fontsource-variable/geist` |
| Clean | `clean.css` | Inter | `@fontsource-variable/inter` |
| Modern | `modern.css` | Plus Jakarta Sans | `@fontsource-variable/plus-jakarta-sans` |
| Playful | `playful.css` | Bricolage Grotesque and Nunito | `@fontsource-variable/bricolage-grotesque`, `@fontsource-variable/nunito` |
| Soft | `soft.css` | Figtree | `@fontsource-variable/figtree` |
| Ink | `ink.css` | Newsreader and Libre Franklin | `@fontsource-variable/newsreader`, `@fontsource-variable/libre-franklin` |

Load the fonts your preset uses. The table names a Fontsource package for each; Google Fonts works too. Fontsource's variable packages name the family `"Geist Variable"`, so every font stack names both, `"Geist", "Geist Variable", ...`: either source works.

## Components

### Shells and recipes

Many components and sections come in families (the navbar, hero, card, footer and so on). Each family has one shell and a few recipes. The shell owns the landmark, the heading levels, the order of the content and any behavior, and it has named slots for the parts that fill it. A recipe is a short file built on the shell that sets one layout, for example `FooterSimple` or `FooterColumns`. Use the recipes on a page, and use a shell alone only to build a layout of your own. A small change inside the same layout is a prop (size, alignment, tone); a different order or structure is a different recipe.

import Button from "@astronomic/ui/components/Button.astro";

- `Navbar`: below the `md` fold point (`lg` with `collapse="lg"`) the links and actions hide and a menu button opens `MobileMenu`. Without JavaScript the menu button hides and the links show instead, as a row of their own under the brand and the end group, each link a box at least 44px tall (the actions stay hidden: repeat one in the `utilities` slot if a page needs it with no script). Use `lg` when the links, actions and utilities need more room, so the row never wraps. The fold points are Tailwind breakpoints of their own, `--breakpoint-nav-md` (48rem, as Tailwind's `md`) and `--breakpoint-nav-lg` (64rem, as `lg`), with the variants `nav-md:` and `nav-lg:`. A theme moves one in its own `@theme`, after the kit's `theme.css` (Dispatch: `--breakpoint-nav-md: 761px; --breakpoint-nav-lg: 1100px;`), and the bar, the recipes' layouts, the menu and the sticky inset follow. To override a recipe's layout class through `contentClass` or `linksClass`, use the same variant (`nav-md:pt-0`), so it moves with the fold. The mobile menu shows the `actions` prop; if you only use the `actions` slot, the slot content is shown in the menu instead. The `utilities` slot (search, cart, theme switch) stays visible at every width, next to the menu button; use it for anything with its own script, since slot content moved into the menu is static HTML. The `menu` slot goes into the menu panel after the actions, with or without them: a control that sits in the bar on wider screens but has no room there on a narrow phone (Dispatch's light and dark switch, as a `ModeToggle` with text, below 360px). It is not a copy, so it may hold a part with a script; show each copy at its own widths with your classes. Without JavaScript the panel cannot open, so the `menu` slot is not shown: keep anything that must work with no script in the bar. As the panel opens it moves into `<body>`, or into the closest element with `data-ui-portal` when there is one, for example a part of the page that sets its own tokens, so it never takes the bar's own tokens or styles. Until then it sits, closed, inside the bar's `<nav>`: select the bar's own parts as `header > nav` or by their `data-nav-*` marks, not `header nav`.
- `MobileMenu`: a server-rendered open button and a native modal `<dialog>`, opened with `showModal()` by a small script (`lib/mobile-menu.ts`, about 2KB, once per page), with no island. The browser moves focus into the panel and keeps it there, makes the page behind inert, closes it on Escape and gives focus back to the button; the script also closes it on its close button, on a click on the backdrop and when a link or action in it is followed (a same-page jump too; not when it opens in a new tab), and when the window widens until the button hides, keeps `aria-expanded` on the button, and the page does not scroll while it is open. It slides in from the end (none under reduced motion); with `panel="card"` it drops in as a card under the bar instead, placed by the script as it opens (`--menu-top`, `--menu-left`, `--menu-right` on the dialog), so it follows a sticky bar wherever it sits. Without JavaScript its open button is hidden, so a page that uses it outside `Navbar` shows its links another way. - `Media` frames an image in a fixed `ratio` with `object-fit: cover`, so any photo fits the shape. `ImageSource` (`src/lib/image.ts`) is a URL or `{ src, width?, height? }`, so Astro's imported image metadata (`import photo from "./photo.jpg"`) works as it is, and its width and height are passed through to stop layout shift; the kit never imports `astro:assets`. So `label` does two things: in `Stats` no one sees it (it is the region's `aria-label`); in `LogoStrip` it is a visible line of text above or beside the logos. The recipes set only the shell's class props, and pass on only an item's own fields, so a CMS entry's other fields never reach the markup. An empty `items` list renders an empty list: guard it in your page.
  - `Testimonials` holds the quotes in one `<ul role="list">`, or one quote in a plain box (`TestimonialQuote`). `Testimonial` is a `<figure>`: the title, the quote in a `<blockquote>`, then the caption (the avatar, the name, the role and company in `[data-testimonial-byline]`, the logo).
  - `Stats` is one `<dl>`: each stat a `<div>` with the label (`<dt>`) first in the source, so a screen reader reads "Projects shipped: 120", and the value shown first. Each stat is a named container (`stat`), so its value, in the `stat` role, sizes to its own column, on one line (never split mid-number). The label is in the text color and the optional line under it small and muted, so the value, the label and the line are three tiers. No count-up: the numbers are text.
  - `LogoStrip` is one `<ul role="list">` named by the heading or the label. Each logo is `h-logo` tall (`--ui-logo-h`) and at most `max-w-logo` wide, and a name shown as text sits in a box at least that tall (`min-h-logo`), so a wrapped row keeps one pitch; a link takes the kit's focus ring and the `rel` for its `target` (`relFor()` in `src/lib/nav.ts`); on hover a name shown as text fades to the muted color and a linked image to 70% opacity (an image keeps its own colors, so a color change would not show), with no transition under reduced motion. An image in an `<img>` cannot take the page's `currentColor`: give a one-color mark a fill that reads on the page, light and dark (a mid-gray reads on both). A name shown as text is in the text color, as one-color logo artwork in the page's text color is (Agency's black marks, inverted in dark mode): keep one tone across a strip. Its `align` centers only the header: `LogoStripRow` with `align="center"` centers its row. There is no grayscale prop; filter the images from your own class on the recipe (Agency's `ag-logo-filter`).
  - `Steps` is one `<ol role="list">`: a screen reader hears a list of N items, in order, and never the large number. Each `StepItem` is a named container (`step`), so its number sizes to its column; its text keeps the running-text width (`max-w-prose`). In `StepsList`, from step 10 on the wider number pushes that step's text in a little.
  - Breaking changes: `Testimonial`, `Stats`, `LogoStrip` and `Steps` are now shells or parts, used through the recipes: `Testimonial` alone needs `headingTag`, and a page uses `TestimonialQuote` (one large quote) or `TestimonialGrid`; `Stats` becomes `StatsGrid` or `StatsCards`; `LogoStrip` becomes `LogoStripRow` (the old row) or `LogoStripGrid`, and ignores `logo.alt`; `Steps` becomes `StepsColumns` (the old layout, now with a hairline above each step) or `StepsList`. The old `Stats` was the `<dl>` itself, so a `class` or attribute on it styled the list; now they land on the root (the `<section>` or the `<div>`). The old `LogoStrip` laid out a wrapping row on its own; the shell alone now stacks the logos, so use `LogoStripRow` for the row. `Steps`' `headingTag` (the step titles) is now the recipes' `itemHeadingTag`, and `headingTag` sets the section heading. The steps data type is `StepsItem` (`StepItem` is now the part).
- The team, posts, contact and newsletter families follow the same pattern. Each shell (`Team`, `Posts`, `Contact`, `Newsletter`) is, with a heading, a `<section>` named by it, then `SectionHead` a block above the body; without one, a plain `<div>`. Each root is a named container (`team`, `posts`, `contact`, `newsletter`). The recipes set only the shell's class props and pass on only an item's own fields. Pro adds two recipes to each family, on the same free shells.
  - `Team` holds the people in one `<ul role="list">`; with no people the list is left out. Each `TeamMember` is a named container (`team-member`), so its initials and its quote size to the person's own box. With no photo, the initials fill the photo box in display type, so a row of people never breaks. Each name is an item heading, one level under the section heading.
  - `Posts` holds the posts in one `<ul role="list">`, each an `<article>`. With no posts the list is left out, and `empty` shows in its place. The title is the only link to a post, and there is no "Read more". A long word in a title breaks inside its card or row. Each recipe takes `locale` and passes it to every post.
  - `Contact`'s body is a box, not a list. `ContactInfo` is a `<dl>`. The email breaks after the @ first, and only breaks inside a part that is too long for the box, so it never runs out of a narrow column.
  - `Newsletter` with `tone="band"` sits on `surface-band` (the band when a preset sets `--ui-band`, else the page). A shell cannot pass the tone into its slot, so each recipe gives the header the band's text colors and the form `tone="band"` itself. The `Input` keeps its own fill on the band.
  - A recipe with a form takes one `form` prop: the form part's own options (`MessageFormOptions`, `SignupFormOptions`), spread onto it. It must hold the `action`.
- The publishing families follow the same pattern: `ArticleHeader` (shell) with `ArticleHeaderPlain`, `Byline`, `AuthorBox`, and `SeriesNav` (shell) with `SeriesList` and `SeriesPager`. Pro adds `ArticleHeaderCover`, `Paywall` and `StoryRail`.
  - Post pages: the parts size to the box you give them (each is a named container). The post grid, an "On this page" list and a wide breakout are your layout, not the kit's; in a wider box, `ArticleHeader`'s `contentClass` padding keeps the text on your content edge.
  - Pills: `pillClasses({ tone })` in `src/lib/pill.ts` is the one pill shape (`FilterNav`'s filters, a post's topic): `page` (the hairline and muted text, fg on hover, filled when current) or `image` (a `scrim-fg` fill with scrim text, on a photo). The focus ring is yours: `focusRing` on the page, a `focus-on-image` wrapper on a photo.
  - Tap targets: small controls keep their look and take `tap-area`; links in rows that may wrap, and links that stand alone (`Posts`' view-all link, `ContactInfo`'s email and phone, the series link in `ArticleHeader`'s and `Byline`'s meta lines), take `touchBox`. `Byline`'s names are links in a line of text (WCAG 2.5.5's inline exception); as an extra, each name with its joiners is one unit 44px tall on touch, its width the text's, and the name's link covers it. Links inside a sentence keep the text's size (WCAG 2.5.8).
- Heading marks: every section shell (`Features`, `CtaBand`, `Testimonials`, `Stats`, `LogoStrip`, `Steps`, `IndexList`, `IndexTable`, `Marquee`, `Team`, `Posts`, `Contact`, `Newsletter`) takes `mark` and `markLabel` and passes them to its `SectionHead`: a short mark such as "(12)" beside the heading, never inside it, so the heading's name stays plain. With `markLabel`, the mark is hidden from a screen reader and the label is read in its place.
- The inverse surface: `Panel tone="inverse"` is dark on a light page and light on a dark page, in every preset (`--ui-inverse` and `--ui-inverse-fg`, defaults from the page's own pair). It paints the surface with `surface-inverse` and gives its focus ring with `focus-on-inverse`; it rebinds no token, so text on it names the inverse colors (`text-on-inverse`, `text-on-inverse-muted`, `text-on-inverse-mark`, `border-on-inverse-border`) and a Button on it takes `tone="inverse"`. `Footer` and `Testimonials` (with their recipes) take `tone="inverse"` too. `Panel tone="image"` puts your photo under the scrim, dark in both modes, with `focus-on-image`.
- `Marquee` is the marquee family's shell (recipes `MarqueeLogos`, `MarqueeText`, `MarqueeTitle`): a `<section>` named by its heading or its `label`. The items are one list written twice: the copy is `aria-hidden` and `inert`, so a screen reader hears each item once and Tab reaches each link once. It moves only where motion is allowed (see Motion); under reduced motion or the calm setting it is one still copy that wraps onto more lines, with nothing hidden. It stops while the pointer is over it and while a link in it has focus, so a link never slides away from the pointer or the focus ring. Anything that moves for more than five seconds needs a way to stop it (WCAG 2.2.2): pass `pause` on the page's first marquee for the one `MotionPause` button, or place a `MotionPause` yourself beside that marquee (in its label column). Right to left, it runs the other way, so `start` is still the start of the line.
- `IndexTable` is the index table family's shell (recipes `IndexTableStacked`, `IndexTableSplit`): a real `<table>` with column headers, named by the heading or `caption`. In a narrow container each row takes two lines (the first cell and the end column, then the rest) and keeps its table roles, so a screen reader still reads rows and cells with their headers. Cell text is text, never HTML.
- `VideoMedia` has no `autoplay` attribute: its script (`src/lib/video.ts`) starts the muted loop only when motion is allowed and the page is not paused, stops it at once when any of those turns off, and pauses it off screen. With no script, the reader gets the poster and the browser's own controls. Its one button keeps its name ("Play: " and the label) and says by `aria-pressed` whether it plays; a press always works. A loop has no captions: for a video with speech, link to a full player with captions.
- `FilterNav` and `Pagination` mark the current item with `aria-current="page"`. `Pagination` shows the first, last and current page with one neighbor each side, and folds the rest into an ellipsis.
- `Prose` styles plain rich-text HTML (headings in display type, lists, links, quotes, code, images, rules, tables) at a 65ch measure, in the `reading` role. Each element rule sits inside `:where()`, so a class on the content wins over it; a link's hover and focus rules keep one pseudo-class of weight, so change them with a `hover:` or `focus-visible:` class. Links take `link-underline`. Prose is a named container (`prose`), so its h2 (the `subhead` role) sizes to Prose's own width, not the screen's. A container has no content width of its own, so in a box that takes its content's width (an `inline-flex`, an `inline-grid`, an `auto` or `max-content` grid track, a float) Prose sizes as 65ch (`contain-intrinsic-inline-size`); a width you set still wins.
- Form fields: `Field` renders the label, hint and error; put an `Input` or `Textarea` with the same `id` in its slot. Link the hint and error with `describedBy()` from `src/lib/field.ts`:

  ```astro
  ---
  import { describedBy } from "@astronomic/ui/lib/field.ts";
  ---
  <Field label="Email" for="email" hint="We reply within two days." error={error} required>
    <Input id="email" name="email" type="email" required invalid={!!error} aria-describedby={describedBy("email", { hint: true, error })} />
  </Field>
  ```

  `tone` is the surface the Field sits on: `page`, `band` (a `surface-band` area: the band's text colors, and `focus-on-band` on the Field) or `cta` (the CTA band: its text color, and `focus-on-cta` on the Field). On `band` and `cta` the error is in the band's text color with a warning icon before it, since no red reads on every band; the control keeps its own fill, so its red edge still shows, and its focus ring is the band's text color (the accent when no preset sets the band), an invalid control's too. A known limit: an Astro slot cannot pass props to its content, so `Field` cannot set anything on the control. Repeat `id` (the same as `for`), `aria-describedby={describedBy(…)}`, `invalid` and `required` on the control yourself, as above.
- Display type: `display-face` (a `theme.css` utility) sets display text's face. It reads `--ui-font-display`, `--ui-display-weight`, `--ui-display-track`, `--ui-display-stretch` and `--ui-display-case`, with the phone stretch cap (see Display tokens below). `heading-face` is the same for small headings, at `--ui-heading-weight` when a preset sets it. `displayType` and `headingType` in `src/lib/display.ts` are these two classes. Use them for your own headings so they follow the preset; they take variants (`md:display-face`).
- Button classes live in `src/lib/button.ts` (`buttonClasses()`), so React islands reuse the same look.

## Forms

`Form` is the form every kit form part is built on: `MessageForm` (Contact) and `SignupForm` (Newsletter). You can build your own form on it too: put `Field`s in its default slot.

```astro
---
import Field from "@astronomic/ui/components/Field.astro";
import Form from "@astronomic/ui/components/Form.astro";
import Input from "@astronomic/ui/components/Input.astro";
---
<Form action="https://formspree.io/f/<id>" honeypot={{ name: "_gotcha" }} submitLabel="Join">
  <Field label="Email" for="join-email" required>
    <Input id="join-email" type="email" name="email" autocomplete="email" required />
  </Field>
  <p slot="note">One email a month.</p>
</Form>
```

- **No script needed.** `Form` is a plain `<form method="post">`. It posts to `action` and the browser checks the fields itself. This is the default (`enhance="none"`) and the safe choice for any endpoint. The order: the hidden fields, the honeypot, the fields, the `extra` slot, the submit Button, the status line, then the `note` slot.
- **`enhance="fetch"`** sends the form in the page and says the result in the status line under the Button. Use it only with an endpoint that answers JSON with a real status code, on the same origin or with CORS. A cross-origin endpoint without CORS still gets the post, but the page cannot read the answer, so it shows the error text and a retry posts again. Success is a 2xx answer with a JSON type, or 204 No Content; a provider that answers an HTML page, even with 200, reads as an error, so give it a plain post.
- With `fetch`, the script checks each field with the browser's checks. A bad field gets its error text under it (the control's `data-error`, else the browser's own message), `aria-invalid` and the error's id in `aria-describedby`, and focus moves to the first bad field; when it has focus already (Enter pressed in it), the status says its error for screen readers instead. A 2xx JSON answer (or 204 No Content) clears the form and moves focus to the status. If the reader edits a field while it sends, success keeps their edits and leaves focus where they are; the status still says it. Any other answer, no network, or no answer within 15 seconds (the send is aborted) shows the error text and keeps what the reader typed. The Button is never disabled: while sending it is `aria-busy`, and a second submit is ignored. The fields need `Field`'s `errorSlot`, so the error node is there before the script fills it (`MessageForm` and `SignupForm` set it for you).
- The script ships only with a `Form` that has `enhance="fetch"` (a small module, once per page; `FormEnhance.astro` renders it after the form), so a page of plain posts ships none. It binds again on `astro:page-load`, so it works with Astro's `ClientRouter`: a page it reaches by a swap that has a fetch form brings the script with it.
- **The status** (`FormStatus`) always sits on its own line under the Button, so a short and a long message show in the same place. With no text it takes no room.
- **The honeypot** (`honeypot: { name }`, off by default) is one empty text field that real people never see: hidden, out of the Tab order and out of the accessibility tree, with no autocomplete. The endpoint rejects a post that fills it. Use your provider's own name for it, and avoid names that autofill knows (`email`, `name`, `url`).
- **Hidden fields** (`hiddenFields: { name, value }[]`) are the extra fields an endpoint wants, such as a tag. The prop is not `hidden`, which is an HTML attribute.
- On a band, `tone="band"` gives the Button, the status and the note the band's colors, and `focus-on-band` on the form.

The form is generic: any endpoint that takes a form post works, through `action`, the field names and `hiddenFields`. No provider is built in. These three rows were checked against each provider's own docs on 2026-10-14. Copy the action from your provider's embed code as it is.

| Provider | Action | Email field | Hidden fields | Honeypot | `enhance="fetch"` |
| --- | --- | --- | --- | --- | --- |
| Buttondown | `https://buttondown.com/api/emails/embed-subscribe/<user>` | `email` | `embed=1`; optional `tag` | none | No. Buttondown asks you not to send it with fetch, because it may show its own CAPTCHA page. Plain post only |
| Mailchimp | `https://<account>.<dc>.list-manage.com/subscribe/post?u=<u>&id=<id>&f_id=<f_id>` | `EMAIL` (`emailName="EMAIL"`) | none | `{ name: "b_<u>_<id>" }` | No. Plain post only |
| Formspree | `https://formspree.io/f/<id>` | `email` | none | `{ name: "_gotcha" }` | Yes. It answers JSON with `Accept: application/json`, and works cross-origin |

## Dates

`PostCard`, `PostRow` and the posts recipes take a post's `date` as `"YYYY-MM-DD"`. A post's date is optional: without it there is no `<time>`, and the reading time stands alone. The kit reads it in UTC, so the day never moves with the reader's or the build machine's time zone. A `Date` works too, and is read in UTC as well: Astro content collections turn `"2026-10-14"` into UTC midnight, so the day stays the same. But a `Date` made from local parts, such as `new Date(2026, 9, 14)`, is local midnight, and east of UTC that is the day before in UTC, so the page shows the day before. Pass the string instead. A bad value (`"2026-02-30"`, an invalid `Date`) stops the build with the value in the message, so no page says "Invalid Date".

`formatDate(date, locale?, options?)` and `isoDate(date)` in `src/lib/date.ts` are the helpers the parts use: `formatDate` gives medium style in English by default ("Oct 14, 2026"; "14.10.2026" with `"de"`), always in UTC, and `isoDate` gives `YYYY-MM-DD` for `<time datetime>`.

## Heading emphasis

A heading may mark one phrase with asterisks: `Built for *the long run*`. With `emphasis`, the part renders `Built for <em>the long run</em>`.

- The heading holds exactly two asterisks, one on each side of the phrase, with no space just inside them. Anything else (one asterisk, three or more, `**bold**`, `* spaced *`) shows as typed. There is no escape.
- `emphasis` is off by default, so a heading shows exactly as typed. It is on `Hero` and its recipes, on `SectionHead`, and on every section shell, which passes it to its `SectionHead` (so on every recipe too, Pro's included). On `TestimonialQuote` one `emphasis` marks both the section heading and the quote.
- `emphasisParts()` in `src/lib/emphasis.ts` splits the string into text parts, and Astro escapes each one: markup in a heading stays text, with or without `emphasis`. No part uses `set:html` for it.
- `plainHeading()` gives the heading with the marker removed, for `<title>`, meta tags, share cards and aria labels. It is not a sanitizer: it returns the text raw, so put it only where Astro escapes it (an expression or an attribute), never in `set:html` or hand-built XML or SVG.
- The kit adds no style to `<em>`; your theme decides how it looks (italic, a weight, a color).

```astro
---
import HeroSplit from "@astronomic/ui/components/HeroSplit.astro";
import StepsColumns from "@astronomic/ui/components/StepsColumns.astro";
import { plainHeading } from "@astronomic/ui/lib/emphasis.ts";
const heading = "Build sites that *last*.";
---
<title>{plainHeading(heading)}</title>
<HeroSplit heading={heading} emphasis />
<StepsColumns heading="How we *work*" emphasis items={steps} />
```

## Motion

Every animation and transition in the kit is written under one gate, the `motion-ok:` variant (`theme.css`): it applies only when the reader has not asked for reduced motion, your theme is not calm and the reader has not pressed `MotionPause`. Without it, the still state shows. Transform and opacity only, with one exception: Pro's work grid fades its photos from gray to color with a short `filter` transition, under the same gate.

Three states on `<html>`:

- `data-motion="calm"`: your theme writes `data-motion="calm"` for its calm setting, on the server. Nothing moves: no marquee, no word fill, no fade-up, no rolling label, no video autoplay and no view transition.
- `data-motion-paused`: the reader pressed `MotionPause`. Every marquee freezes where it is, every autoplaying video stops, and `motion-ok:` is off (the reader's calm). Marquees move only where scripts run (`@media (scripting: enabled)`), so with no script none moves without a pause button. The choice is kept for the visit (`sessionStorage`, key `astronomic:motion-paused`); blocked storage is fine, the pause still holds for the page.
- `data-reveal-ready`: set by the fade-up script once it can run (the browser can watch the view, motion is allowed, the theme is not calm). The fade-up's rules need it.

Write `motionScript` inline in `<head>`, after your styles, so the pause flag and `data-reveal-ready` are on `<html>` before the first paint (nothing shows and then hides), and put the `reveal` utility on `<html>`:

```astro
---
import { motionScript } from "@astronomic/ui/lib/motion.ts";
---
<html lang="en" class="reveal" data-motion={calm ? "calm" : undefined}>
	<head>
		<!-- your styles -->
		<script is:inline set:html={motionScript} />
	</head>
```

The fade-up marks: blocks rise gently into place as they enter the view, once.

- `data-reveal`: the element rises (its delay from an inline `--reveal-i`, 90ms a step).
- `data-reveal="kids"`: its children rise one after another. Wrap a button or link that would be a direct child, or the rise replaces its own hover transition.
- `data-reveal="hero"`: a kit hero's text rises line by line (the eyebrow, the heading, the lead, the actions).
- `data-reveal="items"`: the items of its list rise one after another.

Content is visible by default: with no script, with reduced motion, under calm and in print, nothing is hidden and nothing moves. View transitions are your theme's choice (`@view-transition`); a part's `transitionName` is set only under `motion-ok:`, and `theme.css` turns the transition's own animations off under reduced motion and calm.

## Rolling links

`Button` takes `roll`: on hover and keyboard focus its label rolls up and the same words roll in from below. `Navbar` (and every recipe) takes `roll` too, for each link label in the bar and in the menu; the index and the badge stay put. Any link can do the same with the `text-roll` utility (`theme.css`): put `text-roll` on the link and wrap its label in two spans, the inner one carrying the same words in `data-label`.

```astro
<a href="/work" class="text-roll">
	<span data-roll><span data-roll-label data-label="Work">Work</span></span>
</a>
```

`data-roll` clips; the copy is `data-label` drawn as `::after` with empty alt text, so a screen reader reads the label once. Keep `data-label` the same plain words as the label (Button's `rollText()` in `src/lib/button.ts` gives them from rendered HTML). The move is a translate only, under the motion gate (the `motion-ok` variant): nothing moves with reduced motion, under the theme's calm setting (`data-motion="calm"` on `<html>`), or on a disabled control. Hover counts only on a device that hovers.

## Your own images

`Media`, and the parts and recipes that show a photo (the parts `TeamMember` and `PostCard`, which also take `imageSizes`, the hint they pass on; the recipes `HeroCover`, `TeamGrid`, `PostGrid`, and Pro's `TeamList`, `TeamSpotlight`, `PostFeatured`, `ArticleHeaderCover` and `CardResult`), take `imageComponent`: your component draws the photo, the kit draws the frame. The kit needs no image package. Your component gets `ImageComponentProps` (`src/lib/image.ts`): `src` exactly as you passed it, `alt`, `width`, `height`, `loading`, `decoding`, `sizes` (the recipe's hint for its layout; approximate, since recipes size by container), `class` (fills and covers the frame; put it on the `<img>`) and `style` (only the focal point; forward it if you set `focalPoint`).

Astro's `<Image>` works as it is when `src` is an imported image:

```astro
---
import { Image } from "astro:assets";
import TeamGrid from "@astronomic/ui/components/TeamGrid.astro";
import ada from "../photos/ada.jpg";
---
<TeamGrid items={[{ name: "Ada Brook", role: "Design lead", image: { src: ada } }]} imageComponent={Image} />
```

Astro writes a `srcset` when `astro.config` sets `image: { layout: "constrained" }`.

For a CMS, write a small wrapper. Pass your own image object as the photo's `src`; the wrapper gets it back whole. EmDash:

```astro
---
// src/components/KitImage.astro: the kit's photos through EmDash's responsive <Image>.
import type { ImageComponentProps } from "@astronomic/ui/lib/image.ts";
import { Image } from "emdash/ui";

type Props = ImageComponentProps;
const { src, alt, loading, sizes, class: className } = Astro.props;
// The page passes { src: url, emdash: entry.data.photo } as the photo's src.
const value = typeof src === "string" ? src : (((src as { emdash?: unknown }).emdash ?? src.src) as Parameters<typeof Image>[0]["image"]);
---
<Image image={value} alt={alt} priority={loading === "eager"} sizes={sizes} class={className} />
```

On the page, build the photo object in a `.map()` before the items. TypeScript rejects the extra `emdash` field in an inline `items` literal, but not in a value built first:

```astro
---
import TeamGrid from "@astronomic/ui/components/TeamGrid.astro";
import KitImage from "../components/KitImage.astro";

// entries: your team entries from EmDash, each with a photo field.
const people = entries.map((entry) => ({
	name: entry.data.name,
	role: entry.data.role,
	image: { src: { src: entry.data.photo.src, emdash: entry.data.photo } },
}));
---
<TeamGrid items={people} imageComponent={KitImage} />
```

The Agency theme ships one.

## Lightbox

`LightboxCentered` and `LightboxBar` open an image large over the page, with its caption, a counter and prev and next. They work on the image links you already have: mark each link with `lightboxAttrs()` and render one lightbox anywhere on the page. The link's `href` is the large image; with no JavaScript it is a plain link to that file.

```astro
---
import LightboxCentered from "@astronomic/ui/components/LightboxCentered.astro";
import { lightboxAttrs } from "@astronomic/ui/lib/lightbox.ts";
import desk from "../photos/desk.jpg";
import shelf from "../photos/shelf.jpg";

const photos = [
	{ photo: desk, alt: "A laptop and a cactus on a wood desk", caption: "The studio desk." },
	{ photo: shelf, alt: "Two plants on a shelf", caption: "Plants by the window." },
];
---
<ul>
	{photos.map(({ photo, alt, caption }) => (
		<li>
			<figure>
				<a href={photo.src} {...lightboxAttrs({ group: "studio", width: photo.width, height: photo.height })}>
					<img src={photo.src} alt={alt} width={photo.width} height={photo.height} />
				</a>
				<figcaption>{caption}</figcaption>
			</figure>
		</li>
	))}
</ul>
<LightboxCentered />
```

- `lightboxAttrs({ group, caption, srcset, sizes, width, height })` returns plain `data-lightbox-*` attributes, so you can write them by hand too. Prev and next walk every visible link with the same `group`, in page order (a link that is `display:none`, `visibility:hidden` or inside `[inert]` is left out), and wrap at the ends; `""` (the default) is a set of one, which shows no prev, next or counter. `srcset` (with `sizes`, `100vw` by default) lets the browser pick the large file; `width` and `height` keep the large view's shape while it loads.
- The caption is `caption`, else the text of the `<figcaption>` of the link's closest `<figure>`, else none. It is plain text, never HTML.
- The large image's alt is the alt of the link's own `<img>`, as you wrote it: `alt=""` stays empty, and the caption still describes the dialog.
- One per page. It is a native modal `<dialog>` with a small script, no framework: focus moves to the close button (with its ring when opened from the keyboard, without it after a click or a tap), stays inside, and goes back to the link of the image shown last (or to the link that opened it, if that one is hidden by then). The arrow keys, Home, End and a sideways swipe move through the set. A long caption scrolls inside its box, and is then a Tab stop so the keyboard can scroll it. A click beside the picture closes it; a drag that starts on the picture or the caption (selecting the caption's text, say) does not. The page behind does not scroll (the same rule as `MobileMenu`, through `lib/modal.ts`).
- A link with a `target` or a `download`, and a click with a modifier key, are left to the browser. The script takes a link's click in the capture phase on `document`, before your own click handlers on the link run, so calling `preventDefault()` there does not stop it: to keep a link out of the lightbox, leave `data-lightbox` off it (only a capture listener on `window` runs earlier).
- It works with ClientRouter as it is: it takes the click before the router, closes when the page changes, and uses the new page's lightbox after a swap.
- With EmDash, write the attributes in your theme's own image renderer (the one that draws images in your rich text), with a large `href` such as the original file. The kit never imports EmDash.
- Not there yet: zoom to actual size, a link per image (a URL for each), preloading the next image, and a filmstrip of thumbnails.

## Site search

A search dialog in the kit's look, on the free `@astronomic-dev/search` package: it indexes your pages and their headings at build time and loads only when a visitor reaches for search. `SearchClassic` is the dialog, `SearchButton` opens it, and `SearchPage` is the full `/search` page. The kit does not install the package, so a site without search never has it. Install it yourself:

```sh
pnpm add @astronomic-dev/search
```

Add the integration to `astro.config.mjs` (its settings are in the package's README: sources, weights, grouping, facets, several indexes):

```js
import search, { collections, html } from "@astronomic-dev/search/astro";

export default defineConfig({
	site: "https://example.com",
	integrations: [
		search({
			sources: [collections({ docs: { label: "Docs" } }), html({ include: ["/", "/pricing"] })],
			browse: [{ label: "Docs", href: "/docs" }],
		}),
	],
});
```

Put one `SearchClassic` in the layout, a `SearchButton` in the header, and `SearchPage` on `src/pages/search.astro`:

```astro
---
import SearchButton from "@astronomic/ui/components/SearchButton.astro";
import SearchClassic from "@astronomic/ui/components/SearchClassic.astro";
---
<header>
	<SearchButton main />
</header>
<slot />
<SearchClassic />
```

```astro
---
// src/pages/search.astro
import SearchPage from "@astronomic/ui/components/SearchPage.astro";
---
<h1>Search</h1>
<SearchPage />
```

- **Which dialog a button opens.** A button opens the dialog with the same `index`, `types` and `group`. For a second search (a docs search beside the site search, say), add a second dialog and a button with the same three props. The shortcut opens the dialog of the `main` button (or the first button), and focus returns to it.
- **No JavaScript.** The button is a real link to `/search` (or its `href`), and `SearchPage` is a GET form that submits to it. `SearchPage` shows the site's `browse` links, since its results need JavaScript.
- **Loading.** Until first use the page runs only a small script that listens. Hover, focus, a click or the shortcut loads the index and the search code (the kit's tests hold that code under 20 KB gzip, and the listening script under 3.5 KB), and a click while it loads opens the dialog when it is ready. If the load fails, the click follows the link. `SearchPage` loads at once when the URL has a query.
- **The words.** Every label comes from the integration's `strings` setting (US English by default; the package's README lists the keys). A dialog's or a page's `strings` prop changes a few for that one. `SearchPage` adds its own: `label` (the box's name, "Search"), `submit` ("Search"), `showMore` ("Show more results") and `moreShown` ("Result {position} of {total}: {title}", read after "Show more results").
- **The shortcut.** The integration's `shortcut` setting, `["mod+k", "/"]` by default (Cmd+K on Apple devices, Ctrl+K elsewhere). `shortcut: false` turns it off for the site, and `shortcut={false}` on a dialog turns it off for that dialog. A `SearchButton` with `openText` shows the key hint ("⌘K" or "Ctrl K").
- **The URL.** `SearchPage` keeps the query, the type tab and the filter picks in the URL (`/search?q=dark+mode&type=docs&theme=vega`). Typing replaces the history entry and a submit adds one, so Back returns to the last query.
- **Open on a search.** A link can open the dialog with words typed, a type tab and filter picks: give it `data-search-trigger data-search-ui="kit"` (and the dialog's `data-search-index`, `-types` and `-group`, if set), plus the package's `data-search-query`, `data-search-type` and `data-search-filters` (`theme=lodestar`). Its `href` is the same search on `/search`, for no JavaScript: `<a href="/search?q=lodestr" data-search-trigger data-search-ui="kit" data-search-query="lodestr">`. It opens the page's one dialog, and the shortcut stays the main button's. The package's README has the details.
- **One kind of dialog per page.** Use the kit's dialog or the package's default one (`SearchLink`), not both on one page. Each skips the other's buttons (`data-search-ui="kit"`), so they never fight.
- **Strict CSP.** The scripts are files, never inline. The settings reach the script in a `<script type="application/json">` block, which never runs, so `script-src 'self'` allows it. The styles are the kit's classes in your CSS. (Astro's `ClientRouter` writes an inline style of its own, which a strict `style-src` refuses.)
- **Analytics.** The dialog and the page fire the package's `search:query`, `search:select` and `search:noresults` events, which bubble to `document`. The package's README has Plausible and Google Analytics examples.
- **The same keys as any dialog.** It is a native modal `<dialog>`: the page behind does not scroll (the kit's one scroll lock, `lib/modal.ts`). Up and Down move through the results with focus in the box, Enter opens one, Cmd or Ctrl+Enter opens it in a new tab, and Escape clears the box, then closes. ClientRouter works as it is.
- **Your own recipe.** Build on `Search.astro` with class hooks only, as `SearchClassic` does: a recipe takes `SearchRecipeProps` (the shell's props less the hooks) and passes them on.
- **Preview pane.** A recipe with a pane that shows the selected result beside the list is planned for Pro, not built yet. The shell already has its `preview` slot.

## Popover

A button that opens a small panel over the page: the browser's own `popover`, with no library. The panel holds whatever you put in it. For choices, use real checkboxes and radios through `PopoverGroup` and `PopoverOption`: they submit with the form around them, with or without JavaScript.

```astro
---
import Popover from "@astronomic/ui/components/Popover.astro";
import PopoverGroup from "@astronomic/ui/components/PopoverGroup.astro";
import PopoverOption from "@astronomic/ui/components/PopoverOption.astro";
---

<Popover label="Home type" summary="choices" anyText="Any type" countText="{n} types">
	<PopoverGroup legend="Home type" legendHidden>
		<PopoverOption type="checkbox" name="type" value="house">House</PopoverOption>
		<PopoverOption type="checkbox" name="type" value="condo">Condo</PopoverOption>
	</PopoverGroup>
</Popover>

<Popover label="Price" summary="range" anyText="Any price" cols={2}>
	<PopoverGroup legend="Min" end="min">
		<PopoverOption type="radio" name="price-min" value="" checked>No min</PopoverOption>
		<PopoverOption type="radio" name="price-min" value="900000">$900K</PopoverOption>
	</PopoverGroup>
	<PopoverGroup legend="Max" end="max">
		<PopoverOption type="radio" name="price-max" value="" checked>No max</PopoverOption>
		<PopoverOption type="radio" name="price-max" value="1500000">$1.5M</PopoverOption>
	</PopoverGroup>
</Popover>
```

- `summary="choices"` writes the trigger's words from the checked options ("Any type", "House", "2 types"). `summary="range"` writes them from the two `end` groups ("$900K to $1.5M", "$900K+", "Up to $1.5M") and disables a Max at or below the Min, and a Min at or above the Max. Option values must be numbers for that; the empty value means no pick.
- The server draws `triggerText`, which defaults to `anyText`: pass the right words when the page opens with something picked.
- Your own script that sets the controls (a form reading the URL) fires no change event, so call `syncPopover(root)` from `lib/popover.ts` after, with the `[data-popover]` element. `choicesText`, `rangeText` and `rangeBlocked` are exported too, for a server or a test.
- A mode switch that makes Price into Rent calls `setPopoverWords(root, { label, anyText })` from `lib/popover.ts`: it changes the trigger's name, the panel's name and the words for nothing picked, then syncs.
- A picked option is never disabled, so a page may open on a Min equal to the Max. An option you marked `disabled` stays disabled. `disabled` on `Popover` disables the trigger and the panel's controls, so they do not submit.
- Enter on a checkbox or a radio in the panel picks it and does not submit the form. Without JavaScript Enter submits the form, as it does on any checkbox.
- Escape and a click outside close the panel. Tab moves through the panel and on past it, and the panel stays open until a click elsewhere or Escape; that is the browser's behavior for a popover. Focus goes back to the trigger, unless the press that closed the panel landed on another control. A panel with nothing to focus takes focus itself.
- The name reads "Home type: 2 types". Do not point a `Field`'s `for` at the trigger: a label replaces the button's own words, and the current value is lost. With a `trigger` slot the words are yours, so write the name in them. The slot is content inside the button, so it must not hold a link or a button.
- The panel sits under the trigger and flips when it does not fit. On a phone it is full width with a small inset. When it fits neither way, it takes the height there is and scrolls inside. A browser with no anchor positioning shows it centered on the screen.
- `--ui-popover-shadow` (optional) sets the panel's lift. The panel is `bg-surface` with the page's text, hairline and focus ring.

## Listings and filters

The listing card and the filters read one fields list. The parts never know your listing type: you pass plain data.

```astro
---
import ListingCardInset from "@astronomic/ui/components/ListingCardInset.astro";
import { checkFields, type ListingField } from "@astronomic/ui/lib/listing.ts";

const fields = checkFields([
	{ key: "price", label: "Price", labels: { buy: "Price", rent: "Rent" }, kind: "range", format: "price", period: { buy: "once", rent: "month" }, steps: { buy: [500000, 750000, 1000000], rent: [2000, 3000, 4000] }, card: false, resetOnMode: true },
	{ key: "beds", label: "Beds", shortLabel: "bd", kind: "range", bound: "min", format: "integer", steps: [1, 2, 3, 4] },
	{ key: "sqft", label: "Sq ft", format: "area" },
	{ key: "type", label: "Home type", kind: "choice", multiple: true, options: [{ value: "house", label: "House" }, { value: "condo", label: "Condo" }] },
] satisfies ListingField[], ["buy", "rent"]);
---
<ListingCardInset listing={home} fields={fields} mode="buy" />
```

- **The fields list** (`ListingField`, `src/lib/listing.ts`): `key` (the key in each listing's `values` and the URL parameter: lowercase letters, digits and "-"; not `q`, `mode`, `sort` or `page`), `label`, `labels?` (per mode), `shortLabel?` (for tight places, "bd"), `kind?` (`range`, `choice` or `toggle`; unset: shown on the card, not filtered), `format?`, `unit?`, `steps?` (a range's Min and Max steps, per mode when they differ), `period?` (a price: `once` or `month`, per mode), `bound?` (`min`: one "at least" select; `both`, the default), `options?` (a choice's `{ value, label }`), `multiple?` (several options at once, as chips), `anyText?` and `countText?` (the words of a dropdown: nothing picked, per mode if they differ, and two or more choices), `card?` (default `true`: in the fact strip), `resetOnMode?` (cleared when the mode changes, as the price). `checkFields(fields, modes)` returns the list, and throws naming the field on a bad, reserved or repeated key, a range without steps, a choice without options, an option value with a comma or used twice, or a per-mode setting that misses a mode, so a mistake fails the build.
- **Formats** are US English: `integer` "4", `decimal` "2.5", `area` "1,840", `year` "1926", `price` "$1,125,000" (or "$3,150/mo" for a month's rent), `text` as given. A choice shows its option's label. `formatPrice(price, { short: true })` gives "$1.13M" for a pin. A missing or bad value prints nothing, and its cell hides.
- **The URL.** The Filters form is the one owner of the URL (`src/lib/filter-state.ts` has the codec). The page is in the path, as your server's pages are (`/search/`, `/search/page/2/`), so a static site serves every page. The query holds the rest: `q=<text>`, `mode=<mode>`, `<key>=<min>-<max>` (either side may be empty: `beds=3-`), `<key>=<a>,<b>` (a choice, in option order), `<key>=1` (a toggle) and `sort=<id>`. Defaults are left out and the keys keep one order, so one state has one URL. A bad value is dropped.
- **`filters:change`** fires on the form once per change, with `detail: { state, kind, source }`: `state` is the whole search (`q`, `mode`, `filters`, `sort`, `page`), `kind` how the URL changed (`push` for a mode or a page, `replace` for the rest), and `source` is `load`, `user` or `popstate` (Back and Forward). A text box fires after 300 ms of no typing, or at once on Enter. The form never submits. A pager link with a script fires `filters:page` (`detail: { page }`) on the form, and the filters set the page and push the URL.
- **Dropdowns.** `dropdown` on `Filters` or `FilterBar` (or on `FilterChoice` and `FilterRange` alone) draws one choice and a range with `bound: "min"` (Beds, Baths) as a `Select` with `picker`, which closes on pick, several choices as checkboxes in a `Popover`, and a range as Min and Max radio lists in one. `ResultsHead` has its own `sortPicker` for its sort, since it is not inside the filters; pass both. In `FilterBar`, a set field has an accent label and a thin underline. Off by default. The controls' names and values, the URL, `filters:change`, the chips and Clear are the same either way. A field's `anyText` (per mode if you like: `{ buy: "Any price", rent: "Any rent" }`) is its words for nothing picked, on a trigger and in a select's first option; `countText` ("{n} types") is a trigger's words for several. CSS first and no library: decision 0002 has why, and what each browser draws.
- **No search in the free kit.** The free filters keep the state and fire the event; something on the page must listen. Listen for `filters:change` and filter your own server-rendered cards, or use Pro's search results, which listen for you. With no script the form is hidden and your list shows every listing.
- **Save** keeps listing ids in the reader's own browser (`localStorage`, no account), one list per name: the storage key is `astronomic:saved:<list>`, `astronomic:saved:homes` by default. After a Save click, or a change in another tab, `saved:change` fires on the document with `detail: { list, ids }`. A Saved homes page reads the same list with `readSaved(list, localStorage)` from `src/lib/saved.ts` and follows `saved:change`. With storage blocked (a private window, a full quota), the list lives in memory for the page, and nothing breaks.
- **The same card in the browser.** `listingCardView()` (`src/lib/listing-card.ts`) gives every text a card shows. The server renders with it, and `fillListingCard()` clones a `<template>` of the same card and fills it with text and attributes only, never HTML. So a card a script adds matches the server's.

## Trades parts

The parts for a trades or home services site: proof, a number to call, and the towns you serve.

- **The pill token and concentric corners.** `--ui-radius-pill` (optional; fully round by default) sets the corners of round-ended controls: an icon-tile Button and an option chip take `rounded-pill`, read on the element itself, so a wrapper that sets the token reaches them. A tile or mark inside takes `rounded-nested`: the outer radius less the gap between the two edges (`--nest-gap`), never below 0, so the two corners run parallel. A card-radius box that holds a tile takes `rounded-card-nest`. One rule for every nested corner, in `theme.css`.
- **The option chip.** `lib/chip.ts` holds the one chip look that `FilterChoice` and Pro `QuotePicker` share: a checkbox or radio drawn as a pill, with its check shown when picked, not only a color.
- **The accent surface.** `surface-accent` paints the accent with its own text color (`--ui-accent-fg` on `--ui-accent`) and rebinds no token. On it, text takes `text-on-accent` and `text-on-accent-muted` (the optional `--ui-accent-muted`, 90% accent-fg by default), rules take `border-on-accent-border`, a Button takes `tone="accent"`, and the surface takes `focus-on-accent`. The pairs are in the token manifest (`accentPairs`) and checked in every preset. `GuaranteeStrip` and `EmergencyBanner` use it. Never white on the accent.
- **`tileMotion`** on `Button` sets how an `iconTile` icon moves on hover and keyboard focus: `turn` (default) turns it -45°; `slide` moves it out past the tile's end while a copy moves in from the start. Still under reduced motion and the calm setting.
- **`PhoneLink` and the Navbar's `phone`.** `PhoneLink` is a `tel:` link with your icon, small words over the number, and `urgent` for an emergency line. Navbar's `phone: { number, label?, icon, callText?, iconOnlyBelow? }` puts one in the end group at every width (the number above the fold point, a 44px round icon link below it, the same name; the fold point is `collapse` unless `iconOnlyBelow: "nav-phone"` moves it to theme.css's `--breakpoint-nav-phone`, 48rem by default, set in your theme's `@theme` in the same unit as the other two, so the number stays after the links fold) and adds a "Call {number}" row to the mobile menu (`callText` sets its words, `{number}` filled in). The `emergency` slot (a `PhoneLink` with `urgent`, say) goes first in the end group.
- **`telHref(number)`** (`src/lib/phone.ts`) gives the `tel:` link for a number as you write it: a leading + kept, letters read as their keypad digits, everything else dropped (`"(555) 010-0142"` to `tel:5550100142`, `"1-800-FLOWERS"` to `tel:18003569377`), an extension ("ext. 23", "x23", "#23") after a comma, the pause before it dials (`tel:6145550147,23`), and an empty string for a number written with fewer than 3 digits, so no link shows. `phoneLabel(number, words?)` gives the link's name ("Call (555) 010-0142").

## Presets and dark mode

`tokens.css` is the default look, Minimal: ink and grays, flat cards with a hairline, Geist. A preset is a CSS file that overrides `--ui-*` tokens on `:root`. Import at most one, after `tokens.css`. Dark mode follows the OS unless `<html data-theme="light|dark">` is set. `ModeToggle` lets a reader set it: it saves `light` or `dark` in localStorage as `aui-theme` (the design system pages' key too) and sets `data-theme`; the inline `modeScript` (`src/lib/mode.ts`) applies the saved choice in the `<head>` before the first paint. With nothing saved, the page follows the OS. A theme that opens in light or dark whatever the OS passes a base: `modeScriptFor("light")` (or `"dark"`) in the `<head>` sets `data-theme` to it when nothing is saved, and `<ModeToggle base="light" />` treats it as the own look, so a press shows dark and saves it, and a press back to light clears the choice. `modeScript` is `modeScriptFor("system")`.

Optional tokens (components fall back when they are not set). `tokens.css` sets some of them for the default look: `--ui-accent-hover-amount`, `--ui-accent-hover-mix`, `--ui-tint`, `--ui-tint-fg`, `--ui-radius-media`, `--ui-card-media-inset`, `--ui-media-border-w`, `--ui-button-shadow`, `--ui-heading-weight` and, in dark mode, `--ui-media-dim`. A preset that wants a component fallback instead sets the token to `initial` (Clean, Modern, Playful, Soft and Ink do), in its light block and, for a token that `tokens.css` sets in dark mode, in both dark blocks too. Each default below is the component fallback:

- `--ui-accent-hover-amount` and `--ui-accent-hover-mix`: the primary button's hover is the accent at this amount, mixed toward this color. Default: 88% toward `--ui-fg` (the default look sets 82% toward `white`, or `black` in dark mode). The mix is worked out at each element, so an area that sets only `--ui-accent` gets its own hover. Set the mix to another color when a mix toward `--ui-fg` would not show, e.g. `currentColor` (the button's label color, `--ui-accent-fg`) when the accent is the ink color. Do not set it to another token such as `var(--ui-bg)`: that is worked out once on `:root`, so an area with its own colors keeps the root's value.
- `--ui-accent-hover`: the primary button's hover color, set outright. Default: the mix above. An area that changes `--ui-accent` must set it too.
- `--ui-button-border-w`: the button border width. Default: `--ui-border-w`.
- `--ui-button-shadow`: the primary button's `box-shadow`, for an inset edge, an inner highlight or a tinted drop shadow. Default: `none`.
- `--ui-band-button-shadow`: the band primary's `box-shadow` (Button `tone="band"` and `tone="cta"`), for a preset whose button shadow is drawn in the accent: draw it in `--ui-band` and `--ui-band-fg`, with the page colors as their fallbacks, so the edge follows the band fill. Playful sets it. Default: `--ui-button-shadow`. Set `--ui-band` where the preset sets this token, on the same element: a token is resolved where it is declared, so the edge follows the band only there. An area that sets `--ui-band` on its own (one section) gets the page edge, unless it sets this token too.
- `--ui-press-scale`: how far a button shrinks while pressed, e.g. `0.97`. Default: no scale (the 1px press drop stays).
- `--ui-field-bg`: the fill of `Input` and `Textarea`. Default: `--ui-surface`. Keep it solid, e.g. `color-mix(in srgb, var(--ui-fg) 6%, var(--ui-surface-2))`: a see-through fill lets a band behind the field show through, and its text may no longer read. Make it differ from `--ui-surface-2` too, so a field still shows on a quiet fill (the Paywall card).
- `--ui-field-border-w`: the top and side edge width of `Input` and `Textarea`. Default: `--ui-border-w`. The bottom edge always keeps `--ui-border-w` in `--ui-border-control`, so a filled field set to `0px` still shows a 3:1 line. An invalid filled field adds an inset `--ui-danger` ring for the edges it lacks; a disabled field fades to 60% on `--ui-surface-2`.
- `--ui-card-border-w`: the width of a `Card`'s edge (and so the cards in `FeatureGridCards`, Pro's `PricingPlan` and the other parts built on it). Default: `--ui-border-w`. `0px` leaves the shadow alone to lift the card; give `--ui-shadow` enough depth to show it then.
- `--ui-tint` and `--ui-tint-fg`: a second soft color and its text, for the `Badge` pill and the `Avatar` initials. Default: the Badge on `--ui-surface` with a `--ui-border` edge and `--ui-fg` text, the initials on `--ui-surface-2` in `--ui-muted`. Set both, in light and dark, at 4.5:1; the pill's edge takes the tint, so it reads as a fill.
- `--ui-radius-media`: the corners of `Media` images (and so the images in `Card`, `HeroSplit`, `CtaBandImage` and `FeatureRows`). Default: `--ui-radius-card`.
- `--ui-media-border-w`: the width of a `Media` image's edge, drawn in `--ui-border`. Default: `0px` (no edge).
- `--ui-media-shadow`: a `Media` image's `box-shadow`. Default: `none`. A `Card`'s image does not draw it: the card is already its frame, so a mat or ring there would read as a second edge.
- `--ui-media-dim`: a `Media` image's `filter`, e.g. `brightness(0.9)`. Default: `none`. Set it in the dark blocks to take the glare off pale photos on a dark page; keep it slight so photos still look natural.
- `--ui-card-media-inset`: how far a `Card`'s image sits from the card's top and side edges. A card with an image pads its text by the same amount, so the image and the text share one edge (the default look and Clean set `12px`); a card without one keeps the padding, and so does `CardOverlay` (its image is behind the text). `0px` is a full-bleed image: the text then keeps the padding. Default: the padding (`calc(var(--ui-space) * 6)`). The image's corners are then `--ui-radius-media` if set, else the card radius less the inset, so they stay concentric with the card's.
- `--ui-nav-bg` and `--ui-nav-blur`: the `Navbar`'s fill and its `backdrop-filter` (e.g. a translucent `--ui-nav-bg` with `blur(16px)` for a glass bar; it shows through only where something scrolls under it, so make the bar sticky in your layout for that). Default: `--ui-bg` and `none`. `--ui-band` wins over `--ui-nav-bg`. Set `--ui-nav-bg` in light and dark.
- `--ui-nav-offset`: the page's `scroll-padding-top` when it has a sticky `Navbar`, so in-page jumps and focused elements land below the bar. Default: `6rem` for one row, `9rem` for two (`NavbarStacked`, above its fold point only), and `1.5rem` more when the bar floats, a little over the kit's bars in its presets. Set it to your bar's height, plus a small gap, when your bar is taller (a larger brand, a second row of your own). `theme.css` resolves it into one inset that a sticky box under the bar reads too, as `top-nav-inset` (the inset plus an item gap; an item gap alone with no sticky bar and no `--ui-nav-offset`), so in-page jumps and Pro's `FaqSplit` header stop at the same line. Change the offset with `--ui-nav-offset`, not a `scroll-padding` utility on `<html>`: `top-nav-inset` follows the token, not the utility. A site with its own sticky header (not the kit's `Navbar`) sets `--ui-nav-offset` on `<html>` to its height; `top-nav-inset` then reads it, and the site sets its own `scroll-padding-top` (for example `scroll-padding-top: var(--ui-nav-offset)`).
- `--ui-body-track`: the letter spacing of body text, e.g. `-0.01em` for a face that sets loose. Default: `normal`. `theme.css` maps it to `tracking-body`: put that class with `font-body` on your page's root element (e.g. `<body class="font-body tracking-body">`); text inherits it, and display type and buttons keep their own tracking.
- `--ui-heading-weight`: the weight of small headings in display type (`FeatureItem` titles, and Pro's plan, question and bento titles; `headingType` in `src/lib/display.ts`). Default: `--ui-display-weight`.
- `--ui-bento-row`: the smallest row height of Pro's bento grid (`auto-rows-bento`, every row one height and at least this tall). Default: `11rem`.
- `--ui-notch-angle`: the slope of a notch's walls in Pro's MediaShape, 0deg to 60deg (a bad unit gives 0deg). Default: `0deg`.
- `--ui-notch-radius`: the curve inside a notch in Pro's MediaShape, and the corners of the plate behind its item. Default: `--ui-radius-media`, else `--ui-radius-card`.
- `--ui-notch-gap`: the space between a MediaShape item and the cut's walls around it. The item sits flush with the frame's outer edges, so a Badge or Button edge becomes the photo's outline; with `notch-float` on the item (for bare text) the gap goes on the outer sides too (for a bite, added to its radius). Default: `0.5rem`.
- `--ui-cut-size`: how far `Media`'s cut corner (`shape="cut"`) reaches along each edge: the slice stops at most at half of each side, and the rounded joins curve in from up to `--ui-cut-r` further. Default: `2.5rem`.
- `--ui-cut-r`: the rounding on the joins of `Media`'s cut corner, at most 30% of the cut. Default: `5px`.
- `--ui-logo-h`: the height of each logo in `LogoStrip` and its recipes (`h-logo`, which `cn()` merges like any height, so a class such as `h-8` replaces it; each logo is at most `max-w-logo`, 9rem, wide). Default: `1.75rem`.
- `--ui-icon-stroke`: the line weight of every kit icon (`Icon`, and a React part's own icon through `iconClasses()` in `src/lib/icon.ts`), through the `ui-icon` utility (not a bare `icon`, which collides with icon fonts and CMS HTML). The stroke does not scale, so it is the same at every size. Default: `1.75px`.
- `--ui-inverse` and `--ui-inverse-fg`: the inverse surface (`Panel tone="inverse"`, and `Footer` and `Testimonials` under `tone="inverse"`) and its text. Default: the page's own pair swapped (`--ui-fg` and `--ui-bg`), so it is dark on a light page and light on a dark page. `--ui-inverse-muted` (default `--ui-inverse-fg` at 72% on the fill), `--ui-inverse-border` (24%) and `--ui-inverse-mark` (default `--ui-inverse-fg`) are its muted text, its rules and its marks. Set them in light and dark, at 4.5:1.
- `--ui-fill-start`, `--ui-inverse-fill-start` and `--ui-scrim-fill-start`: where Pro's word fill starts, on the page, on the inverse surface and on a photo. Default: `--ui-muted`, `--ui-inverse-muted`, and `--ui-scrim-fg` at 80% over `--ui-scrim`. Each ends at full ink.
- `--ui-marquee-duration`: how long one marquee loop takes at `speed="normal"` (`slow` is 1.5 times it, `fast` 0.6). Default: `40s`.
- `--ui-panel-inset` and `--ui-radius-panel`: how far a `Panel` sits from the page's sides and the next block, and its corners. Default: `0.5rem` and `--ui-radius-card`.
- `--ui-band` and `--ui-band-fg`: the band, a full-width color region, and its text. The CTA family (`CtaBand` and its recipes) always sits on it (default: `--ui-accent` and `--ui-accent-fg`). `Navbar` and `Footer` move onto it only when a preset sets `--ui-band`; without it they stay on the page (`--ui-bg`, `--ui-fg`, `--ui-muted`). On the band, their text is `--ui-band-fg`, the Navbar's action buttons take `tone="band"`, and the focus ring is `--ui-band-fg`. Set both, in light and dark, at 4.5:1. Content you put in a Navbar's `actions` or `utilities` slot, or in a Footer's slots, keeps its own colors: a kit `Input` or `Button` stays readable on its own surface, and your own text takes the band colors from `text-on-band` and `text-on-band-muted`.
- `--ui-space-section`, `--ui-space-block` and `--ui-space-item`: the spacing roles `section`, `blocks` and `item` (`py-section`, `gap-blocks`, `gap-item`; the blocks role is not `block`, which would clash with `inline-block`). Default: `--ui-space` times 8 and 2.5 for `blocks` and `item`; `section` grows with the screen, `clamp(16 × --ui-space, 8 × --ui-space + 8vw, 32 × --ui-space)` (64px on a phone to 128px from about 1200px in Minimal, 80px to 160px in Soft), since section space is page rhythm and reads the viewport. Each is worked out at each element, so an area that sets only `--ui-space` gets its own gaps. A role a preset sets on `:root` keeps its root size everywhere. Three spacings derive from them: `blocks-item` (`blocks` plus `item`), `group` (twice `blocks`) and `cards` (`gap-cards`, twice `item`: the gap between cards in a grid).
- `--ui-space-cards`: the `cards` role (`gap-cards`, the gap between cards in a grid) on its own. Default: twice `--ui-space-item` (20px in Minimal). A theme sets it for its own card gap, never `--spacing-cards`.

Field edges: `--ui-border-control` is the edge of `Input` and `Textarea`. The edge is the only sign of a text field, so it needs 3:1 on the page and on `--ui-surface`; `--ui-border` stays a decorative hairline.

Display tokens: `--ui-display-weight`, `--ui-display-track`, `--ui-display-stretch` (`font-stretch`, default `100%`; e.g. `118%` for an expanded face, `75%` for a condensed one; needs a variable font with a width axis) and `--ui-display-case` (`text-transform`, default `none`). Every component that shows display type reads all four. Below 640px an expanded stretch is capped at 106%, so wide headings still wrap well on a phone. `--ui-display-scale` (`1` is the plain size; the default look sets `0.94`) multiplies the large display sizes: the `display` role (the `Hero` headings), the `title` role (the `CtaBand` headings; not `CtaBandInline`'s, which is the `lead` role), the `section` role (the section headings), the `stat` role (stat values), the `step` role (step numbers), the `quote` role (`TestimonialQuote`) and the `price` role (Pro's plan prices).

Type roles: `--ui-type-display`, `--ui-type-display-split`, `--ui-type-title`, `--ui-type-section`, `--ui-type-stat`, `--ui-type-step`, `--ui-type-quote`, `--ui-type-price`, `--ui-type-subhead`, `--ui-type-heading`, `--ui-type-lead`, `--ui-type-reading`, `--ui-type-body`, `--ui-type-small` and `--ui-type-eyebrow`, used as `text-display` and so on. `reading` is running text (`Prose`, 1.0625rem, line height 1.7), a step above `body`. `section` is a section's heading (`SectionHead`, `FeatureRows`' row titles), a step under `title` (`clamp(1.75rem, 1rem + 3cqi, 2.75rem)`); `title` is for the band headings (`CtaBand`) and page titles. `--ui-type-section` is optional: unset (a site without `tokens.css`), it falls back to `--ui-type-title`. `subhead` is a heading inside running text (`Prose`'s h2), one step under `section` and above `heading`; it follows the nearest container (`cqi`) but does not take the display scale. The large ones (display, title, section, stat, step, quote, price) follow the nearest container (`cqi`) and take `--ui-display-scale` (see Display tokens above). `--ui-type-stat` is the largest a stat value gets (4.5rem): below it, `text-stat` divides the stat's width (each stat is a container) by the list's widest value in em (`--stat-ems`, which `Stats` sets on its `<dl>` from its items with `widestStatEms()` in `src/lib/stat.ts`; 7.2 without it), so every value in a list is one size, short values come out large, and none wraps or overflows ("12,500,000+" fits a 9rem stat); `--ui-type-step` is a step number (each step is a container), its own role so the stat values can grow without it; `--ui-type-quote` is one large pull quote, below the title role so it never outweighs a section heading; `--ui-type-price` is a plan's price (Pro's `PricingPlan`, each price line a container), up to 3.5rem, below `stat`, since a price sits in a card beside other text: below it, `text-price` divides the line's width by the list's widest price in em (`--price-ems`, which `PricingPlan` sets on each price, from `widestStatEms()` over the list's prices in `PricingCards`; 5 without it), down to 1.5rem, so a long or local price ("CHF 1’299.00") fits a phone card and a short one keeps the full size. `statType` in `src/lib/display.ts` is the class string for a stat: the role in display type, with figures of one width so a row of numbers lines up; `stepType` is the same for a step number, and `priceType` for a price.

Reading widths come in steps, as `max-w-*` classes that `cn()` merges: `max-w-head` (52rem, a section header box), `max-w-lead` (52ch, a lead), `max-w-lead-narrow` (40ch, a lead beside actions or media, a large quote) and Tailwind's own `max-w-prose` (65ch, running text). A `ch` width follows the font size of the element that carries it, so put it on the element with the type role. The kit's components use no literal max width.

Named classes: every value a component reads from a token has a name in `theme.css`, so the components use no `var(--ui-…)` in an arbitrary class and no short form such as `h-(--ui-control-h)`. Use the same names in your own parts; each has a comment in `theme.css`. The ones a buyer meets most:

| Class | What it is |
| --- | --- |

| `border-button`, `border-field`, `border-s-quote` | Button's and the fields' edge widths (`--ui-button-border-w`, `--ui-field-border-w`), and `Prose`'s quote rule (twice the hairline) |

## Design system pages

`@astronomic/ui/system` adds four pages that show a site's design system:

| Route | Shows |
| --- | --- |
| `/system` | The overview: every screen the theme lists, as a live preview, then links to the other pages. |
| `/system/foundations` | Every `--ui-*` color with its live value and contrast, the fonts, a Prose sample, spacing and shape, the theme's own tokens, and theme extras. |
| `/system/components` | Every component in this package, with a line on when to use it. |
| `/system/sections` | The theme's own blocks with real content. |

They exist in `astro dev`. A build adds them only with `ASTRONOMIC_SYSTEM=1`. `astro preview` serves only what the build made.

Turn them on in `astro.config.mjs`:

```js
import { astronomicSystem } from "@astronomic/ui/system";

export default defineConfig({
	integrations: [
		astronomicSystem({
			name: "Agency",
			layout: "./src/system/Layout.astro",
			sections: "./src/system/Sections.astro",
			extras: "./src/system/Extras.astro",
			screens: "./src/system/screens.ts",
			tokens: ["--ag-"],
		}),
	],
});
```

| Option | Required | What it does |
| --- | --- | --- |
| `layout` | yes | A component that wraps each page in the site's look. It gets a `title` prop and a default slot. |
| `name` | no | The name shown on `/system`. Default `"Theme"`. |
| `sections` | no | A component that renders the theme's blocks. Without it, the page says so in one line. |
| `extras` | no | A component with theme items for the foundations page. Without it, the page says so in one line. |
| `screens` | no | A module that exports `screens`, the theme's pages for the overview (see below). Without it, the overview says so in one line. |
| `tokens` | no | Prefixes of the theme's own CSS custom properties to list, e.g. `["--ag-"]`. |
| `route` | no | The route prefix. Default `"/system"`. Change it if the site already uses `/system`. |

Paths are relative to the site root. A `sections`, `extras` or `screens` path that does not exist stops the build with an error.

### Screens

The screens file lists every page the theme provides, with real demo slugs:

```ts
import type { Screen } from "virtual:astronomic-system";

export const screens: Screen[] = [
	{ name: "Case study", path: "/work/northwind-rebrand", description: "One project with its gallery." },
	{ name: "Not found", path: "/no-such-page", description: "The 404 page.", status: 404 },
	{ name: "Search", path: "/search?q=northwind", description: "Search results.", note: "Needs a server build." },
];
```

`path` starts with `/`; `BASE_URL` is added. `note` shows under the screen, for a caveat. `status` is the HTTP status the page answers with (default 200). A bad entry stops the page with an error that names it.

`/system` shows each screen as a live preview: the real page in an iframe, desktop-wide and scaled down to the card. Frames load lazily as you scroll. They are hidden from screen readers and the tab order (`inert`, `aria-hidden`, `tabindex="-1"`); the screen's name is the link.

### Footer links

`@astronomic/ui/system/link` exports two values, each `null` when the pages are off:

- `systemLink`: the start page (with `BASE_URL`).
- `systemLinks`: every page as `{ label, href }` (Overview, Foundations, Components, Sections), for a footer column.

It is a real file that exports `null`; the integration serves the real values in its place, in every build. So a theme layout can always import it, and a site without `astronomicSystem()` still builds, with no links:

```astro
---
import { systemLinks } from "@astronomic/ui/system/link";
---
{systemLinks && (
	<nav aria-label="Design system">
		{systemLinks.map((link) => <a href={link.href}>{link.label}</a>)}
	</nav>
)}
```

Agency adds them as a "Design system" footer column; the starter as a row under its footer. In a normal build they do not render. This is the only system module theme code outside `src/system/` imports.

The pages follow the site's output: static in a static build, on demand in a server build. Values are read live in the browser, so they follow the light and dark switch on the page and any token you edit.
