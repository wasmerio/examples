# 写作风格指南

Wisp 的取向：**安静、准确、克制**。页面里只留下文字，其余退到背后；文章也一样。排版规则的依据是主题的外观规范 `DESIGN.md`（Typography；站点里是 `node_modules/astro-wisp/DESIGN.md`）。

## 语气

- 像对一位同行解释：直接、具体、有判断力。第一人称用“我”或“我们”都可以，但全文统一。
- 先给结论或要回答的问题，再展开。优先正面说明事情是什么、为什么发生、产生什么影响以及可以得出什么判断；开头不写“本文将介绍”“随着……的发展”“众所周知”。
- 不用防御性套话和空转连接词：不要习惯性使用“不能证明”“不足以说明”“不代表”“并不意味着”“不能据此”“不等于”“并不是说”“更准确地说”以及“值得注意的是”“需要留意的是”等缓冲表达，不习惯性套用“不是……而是……”否定绕弯句式；也不要在明确判断后面自动补充“但这不意味着……”之类的免责声明尾巴。
- 避开论文直译腔和生造压缩词：不用“开一条……的轴”“账本”“配方”“物化”“全景”“全解”“解剖”“机理”等生硬套词，能说人话就直接说（例如“方案”“显式展开”“开销对比”“原理”）。
- 能用数字、例子、代码说明的，不用形容词。“快 3 倍”优于“非常快”；删掉空洞的强化副词，如“非常”“极其”“相当”“真正的”“强大的”“革命性的”“一定要”“严格”“彻底”“精准”“天然”“干净”“清晰”（除非指数学严格等价或数值精度）。
- 存在真实工程边界或不确定性时，清楚交代定量触发条件与具体不确定之处；不知道的不写，不编造数据、引用、链接。
- 不连用感叹号，正文原则上不用感叹号；不用“让我们一起来看看”。
- 一句话一个意思，从句嵌套超过两层就拆开。常规句子控制在 30–65 字（复合句尽量不超过 95 字），不连用多个分号把三四件事焊成一句。

## 中文技术写作规范

**标点**

- 中文语境用全角标点：，。：；！？（）、“”。代码、命令、英文句子用半角。
- 引号统一用中文弯引号 `“”`，不用直角引号 `「」『』` 或直引号 `""`，更不要混用。书名号用《》。省略号用 `……`。
- 句末不用英文句点；括号内是中文用全角括号，括号内是纯英文或代码也建议全角括号包裹。
- 破折号用 `——`（两个字宽），少用。
- 括号里补充英文全称与中文说明时，坚持英文前置：`Self-Attention（自注意力）`；禁止倒写成“中文（缩写）”。

**中英混排**

- **不需要手动加空格**。中英文之间、中文与数字之间的间距由 CSS `text-autospace` 处理，直接写 `使用 Astro 构建`、`共 3 步`（加了也不出错，但保持全文一致，建议不加或统一加）。
- 加粗紧挨中文标点也能闭合：直接写 `**结论。**后文`、`**文字**（括号）`，`**` 后面不用补空格（主题启用了 CJK 友好的强调规则）。
- 英文专有名词保持官方大小写：`PyTorch`、`TypeScript`、`GitHub`。
- 英文单词不要被全角标点包夹后又加空格：写 `支持 Rust，也支持 Go。`，不写 `支持 Rust ，也支持 Go 。`。

**数字与单位**

- 数字用阿拉伯数字；“一个”“第一步”这类固定说法除外。
- 数值与单位之间可以不加空格（`16GB`）也可以加（`16 GB`），全文统一；单位用标准写法（`ms`、`GB`、`MHz`）。
- 百分比写 `35%`，范围写 `3–5` 或“3 到 5”，不写 `3~5`。
- 大数字用阿拉伯数字加单位：`1.2 万`、`3 亿`，或直接 `12,000`。
- 复杂度、变量、公式一律用 `$...$`，不要写成纯文本 `O(n^2)`。
- 纯数字与物理单位不要套反引号 `` `...` ``（写 `1024`，不写 `` `1024` ``）。

**术语**

- 使用业界共识术语与通行简称：首次出现时采用“业界通用英文 + 括号说明”（如 `KV Cache（键值缓存）`、`Prefill（预填充）`），后文直接使用同行日常交流的简称；严禁生造中文直译或跨领域借错词，禁止倒写成漏掉英文全称的“中文（缩写）”（如`高带宽显存（HBM）`）。
- 同一概念全文只用一个译名；通用英文术语（如 `token`、`Logits`、`softmax`、`embedding`、`Kernel`、`Roofline`）保持业界通行写法。
- 缩写首次出现写明“缩写 + 英文全称 + 中文说明”：`RAG（Retrieval-Augmented Generation，检索增强生成）`、`SM（Streaming Multiprocessor，流式多处理器）`。
- 行内代码用于标识符、命令、文件名、参数：`pnpm build`、`src/content`。不要用行内代码做强调或包裹纯数字。

**强调**

- 中文强调只用 `**粗体**`，一段至多一两处。不用斜体（主题不为中文渲染斜体）；西文强调 `*emphasis*` 可用。
- 不用全大写、下划线、颜色、emoji 强调。

## 标题层级

- 正文不用 h1（标题来自 frontmatter 的 `title`）。从 h2 开始，h3 次之，一般不超过 h4。
- **不跳级**：h2 下面才能有 h3。
- **文章标题 `title` 简短聚焦**：点明核心主题即可，不把全文目录或三五个关键词塞进冒号副标题，不放纯文本 `O(...)` 或内部下划线符号。
- **h2/h3 简短自然**：可以用干净的名词短语（“计算步骤”“复杂度”“实现”），也可以用简短自然的问题式或场景式小标题（“为什么要除以 √d”“同一个‘首’字，查表如何不串味”），但一节只讲一件事，避免三四个并列名词拼盘。
- 文章标题（frontmatter `title`）以数字开头时，如“05 MLA 与 KV 缓存”，数字会被拆出来作为大号章节号显示；系列文章想要章节号就这样写，不想要就不要以数字开头。正文 h2/h3 由主题自动编号，不要在标题里手写“1.”“2.1”。
- 标题里不放行内代码 `` `...` ``、纯文本公式 `O(...)`、链接；必须用术语时保持简短。
- 每个 h2 下至少有两段内容；只有一句话的小节合并到上一节。
- 文章通常以“小结”或“延伸阅读”结尾，不写“谢谢阅读”。

## 段落

- 一段讲一件事，段落长度控制在 80–200 字（屏幕约 3–5 行，上限 250 字）。单段新术语与括号说明保持克制。
- 段落之间不用全角空格缩进，不用 `<br>`。
- 长推导拆成“已知 → 步骤 → 结论”，公式单独成行。
- 代码块前一句说明目的，后一句说明关键点或预期输出。

## 列表与表格

- **列表**用于并列的条目、清晰的 3–5 步流程或简短要点（步骤用有序列表，选项用无序列表）。每项 1–2 句，句式统一，不超过两层嵌套；禁用 `- **黑话词头**：上百字长段解释` 的 PPT 提纲体。需要展开因果分析的内容写成段落。
- 列表项以句号结尾与否要全篇统一；短语型条目不加句号。
- **表格**用于多个对象在多个维度上的对比（至少 3 行 × 3 列）。单元格里写短语，不写长句；不要用表格排版。表头明确，不留空单元格，复杂度等写成公式。
- 只有两三个条目的对比，写成句子比表格好。

## 引用块

- 用来引用他人的原话、规范原文或论文摘录，注明出处。
- 不用来做“提示”“警告”“小贴士”。这类内容放进正文，必要时用一句话开头：“注意：……”。
- 引用块不用斜体（样式已处理）。它渲染为浅底「要点块」，没有彩色竖条，不要靠它做装饰。

## 引用与脚注

- **出处用引用，不用文末的「来源」列表。** 正文里来自论文、源码、官方文档、别人博客的事实、数字、结论，在那句话末尾标 `[^key]`，文末写定义。读者在句子旁边就能看到依据，点一下就能核对。语法与渲染见 elements.md「引用（脚注）」。
- **引用还是链接：** 读者需要“去那里看看”的（工具主页、延伸阅读、站内其他文章）用普通链接；某句话的依据用引用。同一来源既要作依据又要给入口时，依据用引用，链接写在定义里。
- **一条引用的格式**（按顺序，没有的项省略，不要编造）：作者或机构，标题（中文书名号或英文引号），出处（会议/期刊 年份、项目名），链接；最后写能锁定内容的信息——论文写版本或章节（arXiv v2、§3.2），源码写 commit 或 tag 和文件路径，网页文档写访问日期（`访问于 2026-08-30`）。
  - 论文：`[^mla]: DeepSeek-AI，“DeepSeek-V2: …”，2024。[arXiv:2405.04434v5](https://arxiv.org/abs/2405.04434v5)，§2.1。`
  - 源码：``[^runner]: vLLM 项目，`vllm/v1/worker/gpu_model_runner.py`，commit `1a2b3c4`。[GitHub](https://github.com/vllm-project/vllm)。``
  - 文档：`[^cuda-graphs]: NVIDIA，《CUDA C++ Programming Guide》CUDA Graphs 一节。[链接](https://docs.nvidia.com/cuda/)，访问于 2026-08-30。`
- **补充说明**也可以用脚注（不打断正文的限定条件、旁注），每条一两句话；需要大段展开就放进正文。
- key 在文内唯一，同一来源复用同一个 key；定义放在文末，按第一次引用的顺序排列。
- 只引用确认存在、确实说了这件事的来源；拿不准的不写。

## 链接

- 链接文字写清目标内容：[Astro 内容集合文档](https://docs.astro.build)，不写“点击这里”。
- 站内链接用绝对路径 `/posts/<slug>/`。外部链接只放确认存在的地址。

## 自检清单

1. 第一段是否说清了结论或要解决的问题？
2. 每个术语是否首次出现时给了英文，之后保持一致？
3. 有没有可以删掉的形容词和副词？
4. 每个 h2 是名词短语，层级不跳？
5. 图、表、代码是否都有文字交代，且图有 alt？
6. check_post.py 无 error，warning 已逐条处理？
